# План проекта: Онлайн-бронирование в барбершоп

> **Стек:** .NET 10 (ASP.NET Core Web API) · React (SPA) · PostgreSQL
> **Модель:** один барбершоп (клиенты + мастера + админ)
> **Оплата:** только на месте (онлайн-оплата в проекте не предусмотрена)
> **Дата составления:** 2026-07-18

---

## 1. Обзор и цели

Веб-приложение для одного барбершопа, позволяющее клиентам записываться к мастерам онлайн, а сотрудникам — управлять расписанием и записями.

**Ключевые ценности MVP:**
- Клиент выбирает услугу → мастера → свободный слот → подтверждает бронь.
- Мастера ведут своё расписание (часы работы, перерывы, отпуска).
- Отзывы и рейтинги мастеров/услуг после визита.

**Явно вне проекта (не реализуется):** уведомления (SMS/email/Telegram), онлайн-оплата, программа лояльности, промокоды и абонементы, мобильное приложение (нативное и PWA).

**Возможное расширение в будущем (не сейчас):** мультифилиальность, интеграция с календарём мастеров, расширенная аналитика.

---

## 2. Роли и права доступа

> **Важно:** учётные записи есть **только у сотрудников барбершопа** (мастера и админ).
> Клиент **не регистрируется и не входит в систему** — бронь гостевая (имя + телефон).

| Актор | Учётная запись | Возможности |
|-------|:--------------:|-------------|
| **Клиент (гость)** | нет | Просмотр услуг, мастеров, свободных слотов; создание брони по имени + телефону; отзыв после визита. Отмену/перенос **не делает сам** — обращается по телефону, изменения вносит персонал |
| **Мастер** | да (email + пароль) | Управление своим расписанием; просмотр своих записей; отметка «выполнено / не пришёл» |
| **Админ** | да (email + пароль) | Управление услугами, мастерами, всеми бронями; аналитика; модерация отзывов |

Реализация: JWT + role-based authorization (`[Authorize(Roles=...)]`) — **применяется только к endpoint'ам персонала**. Публичные endpoint'ы (каталог, слоты, создание брони) доступны без авторизации.

## 3. Аутентификация: email + пароль (только для персонала)

Клиенты не аутентифицируются. Вход используют **только мастера и админ**. Их учётные записи заводит админ (создаёт `User` с ролью Master/Admin, email и начальным паролем); саморегистрации нет.

Поток входа сотрудника:
1. Сотрудник вводит email + пароль.
2. Backend проверяет учётные данные: находит `User` по email, сверяет пароль с хешем.
3. При успехе выдаёт **access token (JWT, ~15 мин)** + **refresh token (httpOnly cookie / БД, ~30 дней)**.

**Хранение пароля:** только хеш (ASP.NET Core `PasswordHasher<T>` / PBKDF2, либо BCrypt). Пароль в открытом виде не хранится и не логируется.

**Смена пароля:** сотрудник может сменить свой пароль; админ может сбросить пароль мастеру.

**Доступ к гостевой брони (без входа):** при создании брони генерируется секретный `ManageToken` (напр. GUID), возвращается клиенту в ссылке на экране подтверждения. По нему клиент **только просматривает бронь и оставляет отзыв** после визита — без учётной записи. Отмену и перенос гость сам не делает: он звонит в барбершоп, изменения вносит персонал.

**Защита:**
- Rate limiting на попытки входа (по email/IP), защита от перебора.
- Требования к паролю (минимальная длина/сложность).
- Rate limiting на публичное создание брони (по телефону/IP) от спама.

## 4. Архитектура backend (Clean / Layered монолит, .NET 10)

```
src/
├── Barberos.Domain/          # Сущности, value objects, доменные правила. Без зависимостей.
├── Barberos.Application/     # Use cases, DTO, интерфейсы, валидация.
├── Barberos.Infrastructure/  # EF Core, PostgreSQL, реализации сервисов, миграции.
└── Barberos.Api/             # ASP.NET Core Web API: контроллеры, middleware, DI, auth, Swagger.
```

**Ключевые технологии:**
- ASP.NET Core Web API (.NET 10)
- EF Core 10 + Npgsql (PostgreSQL provider)
- FluentValidation — валидация входных данных
- Serilog — структурированное логирование
- Swagger / OpenAPI — документация API

**Принципы:**
- Все операции с бронями — в транзакциях, с проверкой конфликтов слотов на уровне БД (unique constraint / advisory lock) во избежание двойного бронирования.
- Перенос брони персоналом = отмена старого интервала + создание нового в одной транзакции под тем же exclusion-constraint.
- **Единая таймзона барбершопа** (IANA, напр. `Asia/Tashkent`) из конфига. Время хранится в UTC, отображается в этой таймзоне. Мультитаймзонность и DST-переходы вне MVP — целевая зона (`Asia/Tashkent`, UTC+5) перевода часов не имеет.

## 5. Модель данных (PostgreSQL)

Основные таблицы:

Клиент — **не** сущность-пользователь. Его данные (имя, телефон) хранятся прямо в брони.

- **users** — сотрудники (только Master/Admin): `id, email (unique), password_hash, name, role, is_active, created_at`
- **refresh_tokens** — `id, user_id, token_hash, expires_at, revoked`
- **services** — `id, name, description, duration_minutes, buffer_minutes, price, is_active`
  - `buffer_minutes` — время после услуги (уборка/подготовка), учитывается при расчёте слотов
  - `price` — `numeric(12,2)`, в **сумах (UZS)**; валюта фиксирована (один барбершоп)
- **masters** — `id, user_id (nullable), name, bio, photo_url, is_active`
- **master_services** — связь мастер↔услуга (кто какую услугу оказывает) `many-to-many`
- **schedules** — рабочие часы мастера `id, master_id, day_of_week, start_time, end_time`
- **time_off** — отпуска/перерывы `id, master_id, start_at, end_at, reason`
- **bookings** — `id, guest_name, guest_phone, manage_token (unique), master_id, service_id, start_at, end_at, status, created_at`
  - `status`: `confirmed / completed / cancelled / no_show` (гостевая бронь создаётся сразу как `confirmed`)
  - `guest_name`, `guest_phone` — данные клиента (гостевая бронь, без учётной записи)
  - `manage_token` — секретный токен для просмотра брони и отзыва клиентом без входа (отмену/перенос гость не делает)
  - `end_at` включает `buffer_minutes` услуги — интервал занятости мастера с учётом буфера
  - **Constraint** от двойного бронирования: exclusion constraint по `(master_id, tstzrange(start_at, end_at))`
- **reviews** — `id, booking_id (unique), master_id, rating (1-5), comment, created_at, is_published`

> `notifications` и `otp_codes` в модели MVP отсутствуют — уведомления и SMS-вход не реализуются (персонал входит по email + паролю).

Диаграмма (упрощённо):
```
             services *─1 bookings 1─* (guest_name, guest_phone — поля брони)
                                  │
             users 1─0..1 masters ─* master_services
                                  │
                                  ├─* schedules
                                  ├─* time_off
                                  └─* bookings
bookings 1─1 reviews
```

## 6. Логика расчёта свободных слотов

Ключевой алгоритм MVP. При запросе слотов для `(мастер, услуга, дата)`:

1. Взять рабочие часы мастера на день недели (`schedules`).
2. Вычесть периоды `time_off`.
3. Вычесть существующие `bookings` в статусах `confirmed`/`completed` (`cancelled`/`no_show` слот освобождают).
4. Разбить оставшиеся интервалы на слоты с шагом (напр. 15 мин), длина слота = `service.duration_minutes + service.buffer_minutes`.
5. Отфильтровать прошедшее время + минимальный буфер до записи (lead time).

Возвращать только реально доступные слоты. Финальная проверка доступности — снова при создании брони (внутри транзакции), т.к. кто-то мог занять слот.

## 7. Уведомления

**В MVP не реализуются.** Никакие автоматические уведомления (SMS / email / Telegram) не отправляются — ни клиенту, ни персоналу.

Клиент получает ссылку для управления бронью (`manage_token`) непосредственно на экране подтверждения после создания брони. Мастера и админ видят новые записи в своём дашборде.

> Уведомления — кандидат на пострелизное расширение (см. раздел 13). Тогда сюда вернутся: таблица `notifications`, фоновый воркер и триггеры (подтверждение, напоминание, отмена, запрос отзыва).

## 8. Frontend (React SPA)

**Стек:**
- React + TypeScript + Vite
- React Router — маршрутизация
- TanStack Query (React Query) — запросы к API, кэширование
- Zustand — состояние (авторизация, язык)
- React Hook Form + Zod — формы и валидация
- Tailwind CSS + shadcn/ui — UI-база (примитивы, формы, диалоги)
- Framer Motion — анимации, переходы, микровзаимодействия (продуманный «pro max» UX)
- 21st.dev — источник готовых красивых блоков (hero, glass-карточки, эффекты), адаптируем под тему
- react-i18next — локализация RU/UZ
- Axios/fetch с интерцептором для refresh-токена

**Дизайн-система (визуальная концепция):**
- **Тёмная тема** — единственная (не переключаемая), тёмная база задаёт настроение барбершопа.
- **Фон** — качественная фотография интерьера барбершопа на всю страницу (fixed/parallax), затемняющий overlay-градиент для читаемости контента.
- **Glassmorphism** — весь передний контент (карточки, панели, навбар, модалки) на «стеклянных» поверхностях: `backdrop-blur`, полупрозрачный фон, тонкая светлая граница, мягкая тень.
- **Изображения** — атмосферные фото мастеров, услуг, работ; ленивая загрузка, `aspect-ratio`, плейсхолдеры.
- **Акцент** — один тёплый акцентный цвет (напр. золото/медь) для CTA и активных состояний.
- **Типографика** — контрастный дисплейный шрифт для заголовков + читаемый гротеск для текста; шрифт должен корректно отображать латиницу (RU + UZ-latn).
- **Доступность** — контроль контраста текста поверх фото (overlay + тени), фокус-стили, `prefers-reduced-motion` для отключения анимаций.

**Локализация (i18n):**
- Два языка: **русский (по умолчанию)** и **узбекский (латиница, o'zbek)**.
- `react-i18next` + JSON-словари `ru`/`uz`; переключатель языка в шапке; выбор сохраняется (localStorage).
- Ключи переводов покрывают весь UI-текст (включая слоган Hero, статусы броней, ошибки форм).
- Форматирование дат/времени/цены (сумы) с учётом локали.

**Экраны:**

*Публичные (клиент, без входа):*
- Главная:
  - **Hero** — фоновое фото барбершопа, стеклянная панель по центру, короткий слоган (2 языка) + подзаголовок + CTA «Записаться». Пример RU: «Классика мужского стиля. Запишись за минуту.» / UZ: «Erkak uslubining klassikasi. Bir daqiqada band qiling.»
  - Секции: услуги, мастера, отзывы, контакты/адрес — на glass-карточках поверх фона
- Каталог услуг
- Страница мастера (профиль, отзывы, рейтинг)
- Флоу бронирования: услуга → мастер → дата/слот → **ввод имени + телефона** → подтверждение (на экране — ссылка с `manage_token`, её нужно сохранить)
- Страница брони по `manage_token` (из ссылки): просмотр деталей + оставить отзыв после визита. Для отмены/переноса — телефон барбершопа

*Мастер (после входа email+пароль):*
- Дашборд с записями (день/неделя)
- Управление расписанием (часы, перерывы, отпуска)
- Отметка статуса записи

*Админ:*
- Управление услугами
- Управление мастерами и их услугами
- Все брони (календарь/список)
- Модерация отзывов
- Базовая аналитика (кол-во записей, загрузка мастеров)

## 9. API (черновой контракт, REST)

```
# Auth (только персонал: мастер/админ)
POST   /api/auth/login              { email, password } → tokens
POST   /api/auth/refresh
POST   /api/auth/logout
POST   /api/auth/change-password    (авторизован)

# Services
GET    /api/services                (публично)
POST   /api/services                (admin)
PUT    /api/services/{id}           (admin)

# Masters
GET    /api/masters                 (публично)
GET    /api/masters/{id}            (публично)
POST   /api/masters                 (admin)     # создаёт мастера + учётку (email/пароль)

# Availability
GET    /api/availability?masterId=&serviceId=&date=   (публично)

# Bookings
POST   /api/bookings                (публично)  { guestName, guestPhone, masterId, serviceId, startAt } → { id, manageToken }
GET    /api/bookings/manage/{token} (публично)  # просмотр своей брони по manage_token (только чтение)
GET    /api/bookings                (master/admin)  # ?from=&to=&masterId=&status=&page=&pageSize=
PATCH  /api/bookings/{id}/status    (master/admin)  # confirmed → completed / no_show / cancelled
PATCH  /api/bookings/{id}/cancel    (master/admin)  # отмена по обращению клиента
PATCH  /api/bookings/{id}/reschedule (master/admin) # перенос: транзакция + повторная проверка слота

# Schedule
GET    /api/masters/{id}/schedule
PUT    /api/masters/{id}/schedule   (master/admin)
POST   /api/masters/{id}/time-off   (master/admin)

# Reviews
POST   /api/reviews/manage/{token}  (публично)  # отзыв по manage_token завершённой брони
GET    /api/masters/{id}/reviews    (публично)
PATCH  /api/reviews/{id}/moderate   (admin)
```

## 10. Нефункциональные требования

- **Безопасность:** HTTPS, хеширование паролей и refresh-токенов, rate limiting (вход + публичное создание брони), `manage_token` как секрет доступа к брони, CORS whitelist, secrets в переменных окружения/секрет-менеджере.
- **Валидация:** на клиенте (UX) и на сервере (истина).
- **Логирование/мониторинг:** Serilog + структурированные логи; health checks (`/health`).
- **Таймзоны:** UTC в БД, единая таймзона барбершопа (IANA) в конфиге.
- **Производительность:** индексы на `bookings(master_id, start_at)`, пагинация списков.

## 14. Решённые вопросы и открытые

**Решено:**
- Гостевая бронь без регистрации (имя + телефон). Отмену/перенос делает **только персонал** по обращению клиента.
- Единая таймзона барбершопа (`Asia/Tashkent`), без DST.
- Цена в сумах (UZS), `numeric(12,2)`.
- Буфер между записями через `services.buffer_minutes`.

**Открытые (уточнить перед стартом):**
1. Политика отмены (за сколько часов до визита можно отменить)?
2. Один слот = один мастер, или есть общие ресурсы (кресла)?
3. Шаг сетки слотов (15 мин?) и минимальный lead time до записи.
